# STAR 法则与项目经历描述

## 一、什么是 STAR 法则

STAR 是描述经历的结构化方法，四个字母分别代表：
- S（Situation，情境）：项目背景、业务痛点、为什么要做这件事
- T（Task，任务）：你在这个项目中承担的目标与职责
- A（Action，行动）：你具体做了哪些关键动作（技术方案、协作推进）
- R（Result，结果）：最终带来什么可量化的收益

它解决的核心问题是：让面试官在短时间内理解"你做了什么、做得怎么样"。

## 二、每一部分怎么写

S（情境）要写清楚业务背景，但不要超过 1 行。重点是让面试官明白这件事有难度、有价值。

T（任务）要明确"你个人的目标"，而不是"团队的目标"。常见错误是写"负责整个系统开发"，让面试官无法判断你的真实贡献。

A（行动）是简历中最有含金量的部分，要体现你的技术判断。不要只罗列技术名词，而要写清楚：为什么选这个方案、过程中遇到什么问题、怎么解决的。

R（结果）尽量量化。可量化的维度包括：
- 性能：响应时间、QPS、P99、吞吐量
- 稳定性：错误率、超时率、可用性
- 成本：资源占用、服务器数量、存储成本
- 业务：转化率、用户数、处理效率

## 三、完整案例

反面写法（只有技术名词）：
> 使用 Redis 和线程池优化了系统性能。

正面写法（STAR + 量化）：
> 在活动高峰期接口 P99 达到 800ms、超时告警频发的背景下（S），负责将核心查询接口的响应时间降到 200ms 以内（T）。通过引入 Redis 缓存热点数据、将串行 IO 改为线程池并发、并针对慢 SQL 添加复合索引（A），最终 P99 降至 180ms，超时率下降 92%，服务器资源占用减少约 30%（R）。

## 四、量化技巧

如果没有精确数据，可以用合理的估算，但必须能自圆其说：
- 用"约""超过""降至"这类词，避免绝对化；
- 优先量化"变化量"而不是"绝对值"（如"下降 60%"比"从 500ms 到 200ms"更简洁）；
- 没有性能数据时，可以量化"覆盖范围"（如"覆盖 12 个业务场景""服务 3 万日活用户"）。

## 五、常见问题

1. 只写结果不写过程：面试官无法判断你的贡献，也无法追问技术细节；
2. 描述过于笼统："负责后端开发"是无效描述；
3. 堆砌技术名词：写了 10 个技术名词却没有一个讲清楚为什么用；
4. 结果无法验证：写"性能提升 300%"却说不清如何测量的；
5. 忽略协作部分：如果做过技术方案评审、推动落地、Code Review，也是加分项，可以写。

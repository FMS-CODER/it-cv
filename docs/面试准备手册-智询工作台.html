01三档项目自述

同一个项目，面试官给你 30 秒、2 分钟、5 分钟，要说的东西完全不同。三档都准备好，问到哪档都不慌。

30 秒版（自我介绍里带过）

我做过一个 AI 简历优化与职业顾问平台，叫智询工作台。技术上用 Spring AI + Vue3，后端是一套自研的 Agent 编排框架：用户提问先由 Planner 做一次结构化决策，判断要不要查知识库、要不要联网，然后进入 ReAct 循环做多轮工具调用，最后流式输出答案。知识库那部分我做了完整的 RAG 链路——pgvector 向量检索加 GTE 语义重排；联网搜索用 SearXNG 加并发正文抓取。整个项目我用 Docker Compose 编排了四个服务，并且写了一套离线评测脚本用 Hit@K、MRR 来量化检索效果。

2 分钟版（项目经历的标准回答）

背景与目标：市面上的简历优化工具大多是一次性问一句答一句，答完就断了，既没有领域知识兜底，也拿不到实时信息。我想做的是一个「有知识库、能联网、会自己决定要不要调工具」的助手，所以做了智询工作台。

技术选型：后端 Spring Boot 3.4 + Spring AI 1.1 接 DeepSeek 做对话、接 DashScope 做 Embedding 和重排；存储用 PostgreSQL 17 加 pgvector，对话记录和向量库放在同一个库；前端 Vue3 + Vite，走 SSE 流式渲染；搜索用自部署的 SearXNG。

我负责的核心：主要是 Agent 编排链路和 RAG 检索链路这两块。

编排上我做了一个统一编排器，把一次请求拆成「意图识别 → 上下文装配 → Prompt 构建 → Planner 决策 → 工具调用 → 流式输出」几个阶段，每个阶段都有耗时埋点和审计日志。工具调用走的是 ReAct 模式，模型每轮可以并行调多个工具，把观察结果回灌到下一轮提示词里，直到它自己判断信息够了输出最终回答。同时我设计了三级降级：ReAct 出异常就退回一次性工具调用再生成，再不行就直接不调工具生成，保证任何情况下用户都能拿到回答。

RAG 上我做的是双路召回：一路用原始问题检索，另一路把原始问题拼上一段「请从简历结构、STAR、项目描述角度补充」的导向语再检索一次，两路按 id 去重合并之后交给重排模型，最后按 0.35 的相似度阈值截断，最多保留 8 条。这样做的原因是单路召回容易被问题的字面表述带偏，加一路导向语能把召回方向往「答案该长什么样」上拽。

结果：我写了一套离线评测脚本，28 条带标注的测试集，Hit@5 做到 92.9%，Hit@10 是 100%，MRR 0.736。因为切分前后我都跑过对比，所以这个提升是可复现的，不是感觉。

3.1 一次请求的完整生命周期

       │     └─ PromptBuilderStep        → 场景化 system prompt / user prompt

       │     ├─ AgentPlannerService.planChat → PlannerDecision（JSON）

追问点为什么 Planner 之后要重跑一遍上下文装配？

因为 Planner 有可能把 needKnowledgeSearch 从 false 改成 true，也可能改写意图。ContextAssemblerStep 里判断的是 context.isKnowledgeRag()，PromptBuilderStep 里拼的是按意图分支的说话风格——这两处都依赖 Planner 的决策结果。如果不在 Planner 之后重跑，第一轮装配出来的就是「按旧开关生成的上下文」，Planner 的决策等于白做。

顺带说一个取舍：重跑意味着 RAG 检索可能被执行两次，是有成本的。我接受这个成本，因为它保证了「决策生效」这件事的正确性，而且第一轮装配时如果本来就开着 RAG，两次检索的 query 一样、结果来自同一份缓存友好的向量库，额外开销可控。

3.2 ReAct 多轮工具调用循环

reactLoop(context, reqVO)
  maxSteps = min(decision.maxReactSteps, context.maxAgentSteps)，下限 1
  if (!decision.initialToolCall) → 直接 streamChatStandard（先让模型直接答）

  Flux.create(sink -> {
    for (step = 0; step < maxSteps; step++) {
      reactPrompt = 基础 system + ReAct 协议 + 历史轨迹 + 工具策略/查询词
      modelResponse = ChatClient...system(reactPrompt).user(userInput)
                              .tools(searchAgentTools).call().content()

      thought    = extractThought(modelResponse)        // 解析「思考：」段
      toolCalls  = extractToolCalls(modelResponse)      // 解析「工具调用：」后的 JSON 数组

      if (toolCalls 非空) {
         逐个执行：knowledge_search → searchKnowledgeWithRerank(query, category, topK)
                   web_search       → searchWeb(query, min(topK, 5))
         把结果拼成 observation，追加进 reactTrace，进入下一轮
      } else {
         // 模型没调工具 = 它认为信息够了
         setReactFinalAnswer(modelResponse); sink.next(...); sink.complete(); return
      }
    }
    // 轮次用尽，再补一次调用，明确要求「基于以上所有工具结果给出最终完整回答」
  })
设计点为什么这么做
用「思考 / 工具调用 / 最终回答」三段式文本协议，而不是直接用原生 Function Calling 换模型的成本低，协议由提示词控制；并且天然能拿到模型的推理过程，可以落进轨迹做审计。代价是需要自己写解析，格式不稳时要兜底——见下面的风险点。
每轮允许并行调多个工具 一次提问往往既要查内部知识库又要查外部实时信息。串行调两个工具就是两倍的往返延迟，并行能把这一步的耗时压到「慢的那个」。
maxSteps 取 Planner 决策与用户配置的较小值 Planner 只管「这个问题大概需要几轮」，用户配置是全局安全上限（默认 3）。取 min 保证任何一方都不会把循环拉爆——这是防止 token 失控和响应过慢的硬闸。
「模型没调工具」直接判定为最终回答 省掉一轮无意义的模型调用，是循环的正常出口。但这里有个隐患，见下面。

必看风险ReAct 模式下的两个真实缺陷（面试官很可能挖）

缺陷一：ReAct 模式下不是「真流式」。循环里每轮用的是 .call().content() 同步阻塞调用，最终的答案是在循环结束后一次性 sink.next() 吐出去的。也就是说走 ReAct 路径时，用户要等所有工具调用结束才看到第一个字，首 token 延迟明显高于标准模式。

我的回答话术：「这是我知道的取舍。标准模式走的是 spec.stream()，是逐 token 流的；ReAct 模式因为要先做工具调用、拿到观察结果，这个阶段本身没有内容可以流给用户，所以只有最终回答那一步是一次性的。如果要优化，我会把中间过程做成'进度事件'——比如每轮调完工具往前端推一条 {stage:'thinking'} 或 {stage:'searching'}，让用户在等待期先看到状态反馈，而不是白屏；同时把最后一轮改成 stream() 拿逐 token 输出。」

缺陷二：工具调用解析失败会静默降级。extractToolCalls 解析 工具调用： 后面的 JSON 数组，如果模型输出格式跑偏（比如多写了说明文字、JSON 顺序不对），解析会失败返回空列表，而空列表在循环里被判定为「模型不调工具」→ 直接把这段文本当最终回答吐给用户。

我的回答话术：「这是一个我事后意识到的问题：格式解析失败和'模型主动结束'在当前是同一个分支，会静默走成最终回答。改进方式是把这两种情况区分开——解析失败时不要当最终回答，而是重试一次或直接降级到 fallback 路径；更彻底一点是改用模型原生的 tool calling，让协议由 SDK 保证而不是靠我解析文本。」

3.3 三级降级与兜底

① ReAct 多轮工具出错 →② Fallback 一次性工具仍不行 →③ Standard 纯生成
层级触发条件行为
① ReAct（默认）Planner 判定需要工具多轮循环，每轮可并行调多个工具
② FallbackReAct 流抛异常（onErrorResume）不再循环，一次性把 Planner 判定需要的工具都调一遍，结果拼进 system prompt，然后走标准流式生成
③ Standard不需要工具 / 步数不足 / Fallback 也判定不需要工具不用工具，直接流式生成；聊天场景仍带历史和落库 Advisor

加分点降级不只是「换个路径」，还包括「保留部分输出」

流式落库的 Advisor 里，doFinally 监听到 SignalType.CANCEL（前端主动断开）时：

  • 如果已经产出了内容 → 把部分回答落库（推理内容 + 正文一起存），用户重进会话能看到；
  • 如果一个字都还没产出 → 不落库，避免写进去一条空消息污染会话列表。

另外用 AtomicBoolean.compareAndSet 保证 doOnComplete 和 doFinally 不会重复写库——因为这两个信号在取消场景下存在竞态。这段是简历里「保留部分输出结果、解决输出异常问题」的实际出处，被问到一定要讲这段代码，比讲概念强十倍。

检索 SQL（真实代码）

SELECT id, content, category, metadata::text AS metadata,
       1 - (embedding <=> ?::vector(1536)) / 2 AS similarity
FROM   resume_knowledge_base
WHERE  embedding IS NOT NULL
  AND  category = ?            -- 可选分类过滤
ORDER BY embedding <=> ?::vector(1536) ASC
LIMIT  ?

这段 SQL 里能讲出四个知识点

  1. <=> 是 pgvector 的余弦距离算子，返回 1 − cosθ，取值范围 [0, 2]。所以 similarity = 1 − d / 2，展开就是 (1 + cosθ) / 2，正好把结果归一到 [0, 1]，0.5 表示正交、1 表示完全同向。（面试官如果问「为什么除以 2」，答这个。）
  2. 索引用的是 HNSW 而不是 IVFFlat：CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)。选 HNSW 的理由是它在召回率和查询延迟上都优于 IVFFlat，而且不需要预先训练、不怕数据增量更新；代价是构建索引慢、占内存更多。当前知识库规模不大，这个代价可以接受。
  3. 维度是 1536（text-embedding-v2），而且 cast 类型不是硬编码的——启动时会从 pg_attribute 读 embedding 列的实际类型（pg_catalog.format_type），动态拼 SQL。为什么这么做：因为项目支持 cv 和 public 两套 schema，cv.vector 可能没建，硬编码 cast 会在某些部署环境直接报错；同时这样也顺带校验了 embedding 维度是否和列定义匹配。
  4. 用原生 JDBC 而不是 MyBatis-Plus：向量插入和距离排序需要显式 cast，ORM 映射反而增加一层不确定性（维度、类型转换）。代价是手写 SQL，收益是检索语义完全可控。PreparedStatement 也保证了不会 SQL 注入。

高频追问为什么用双路检索？为什么阈值是 0.35？为什么还要重排？

双路：单路「用问题去检索」有个固有问题——用户的问题和知识库里的答案，措辞往往不一致。比如用户问「我该不该放照片」，知识库条目讲的是「简历不宜包含身份证号、照片等敏感信息」。字面不重合，向量距离就拉不开。第二路我拼上「请从简历结构、STAR、项目描述、技能关键词、面试话术等角度补充相关条目」，本质是把查询向「答案空间」偏移，让召回方向从「问题长什么样」转向「答案该长什么样」。这是 query rewrite 的一种轻量做法。

0.35 阈值：这个值是结合评测集调出来的。相似度如果设太高（比如 0.7），很多相关但表述不同的片段会被误杀，Hit@K 掉下来；设太低（比如 0.2）则会把「说话方式像、但内容无关」的片段也塞进上下文，反而干扰模型。0.35 是在「召回率」和「上下文纯净度」之间取的一个点。同时我加了最多 8 条的硬上限，防止上下文被检索结果塞爆。

为什么还要重排：向量检索是双塔结构，query 和 document 分开编码，只能算一个粗粒度的语义相似度；重排模型是 cross-encoder，把 query 和每个候选拼在一起过一遍，能捕捉细粒度的语义交互，排序质量明显更好。所以典型做法是「向量检索负责快而全（扩大召回），重排负责准而精」——我先用 expandFactor=2 把候选放大一倍，正是给重排留出重排空间。

3.6 流式输出与对话持久化（Advisor 机制）

Spring AI 的 Advisor 相当于一条环绕链，可以在请求前和响应后插逻辑。我写了两个：

Advisororder职责
CustomChatMemoryAdvisor2按 chatId 查最近 50 条消息（先按时间倒序取 50，再升序还原），转成 UserMessage / AssistantMessage，通过 mutate().prompt(...) 把历史拼进本次请求
CustomStreamLoggerAndMessage2DBAdvisor99聚合流式分片；完成时用 TransactionTemplate 一个事务写「用户消息 + AI 消息」两条，并刷新会话 update_time

讲这个能加分三个工程细节

  • 为什么先倒序再升序：要的是「最近 50 条」。直接升序 LIMIT 50 拿到的是最早的 50 条，多轮对话很容易超过 50 条，拿到的就是最陈旧的上下文。所以先用 createTime DESC LIMIT 50 取最近 50 条，再在内存里升序还原成时间顺序喂给模型。
  • 为什么要显式事务：用户消息和 AI 消息必须同生共死。如果只写进去一条，会话历史就会出现「有问无答」或「有答无问」的错位，多轮上下文直接乱掉。
  • 为什么用 TransactionTemplate 而不是 @Transactional：这段逻辑在 Reactor 的 doOnComplete 回调里执行，不在 Spring 的代理调用链上，注解式事务不会生效，必须用手动事务模板。

简历写点面试怎么说可能追问
有界线程池 + 任务队列替代无限制创建线程，限制并发、降低 OOM 风险 万字级报告生成是长耗时任务。原来一个请求开一个线程，并发上来线程数失控，内存直接顶不住。ThreadPoolExecutor 用有界队列 + 有限核心/最大线程数，把并发压在一个可控水位上。 核心线程数怎么定的？队列满了走什么拒绝策略？为什么不用 Executors.newFixedThreadPool？（答：它是无界队列 LinkedBlockingQueue，任务堆积同样会 OOM，所以必须手动 new 指定有界队列）
多轮续写 Prompt + 上下文注入，解决早停与章节重复 长文本一次生成模型容易早停，或者翻来覆去重复同一段。我把它拆成章节，每轮把「已完成章节的摘要 + 当前要写的章节标题」注入提示词，让模型接着往下写而不是重头写。 怎么检测「重复」？上下文怎么控制不超长？（答：摘要压缩 + 只保留最近 N 章的结构化摘要）
SQL 优化把看板接口从 1.2s 降到 300ms 以内 主要做了两件事：一是消除 N+1，把逐条查询改成一次批量 IN 查询后在内存里组装；二是看执行计划确认走了索引，补了缺失的联合索引，避免回表和临时表排序。另外把不常变的统计数据做了缓存。 怎么定位到是 SQL 的问题？（答：先看接口耗时分布，再用 p6spy / 慢查询日志看具体 SQL 耗时占比，最后 EXPLAIN ANALYZE）

4.4 校园社区分享平台（第三段项目经历）

简历写点面试怎么说
Redis + Caffeine 二级缓存，防雪崩 / 穿透 / 击穿 本地 Caffeine 挡第一层，Redis 挡第二层，DB 是最后一道。热点用户信息走本地缓存可以完全不发网络请求，这是 7ms → 3ms 的主要来源。
· 雪崩：过期时间加随机扰动，避免同一时刻集体失效；
· 穿透：对查不到的 key 缓存空值（短 TTL），挡住反复打 DB 的无效请求；
· 击穿：热点 key 失效时用互斥锁只放一个请求回源，其余等待或返回旧值。
RabbitMQ 广播 + 延时消息 + 延迟双删，保证一致性 本地缓存多实例之间没法互相感知，所以用 MQ 广播把失效消息推给所有实例清本地缓存。延迟双删是防这个场景：线程 A 删缓存 → 写库 → 期间线程 B 读到旧值又写回缓存，所以在写库之后再延迟一段时间二次删除，把可能被写回的脏数据清掉。
兜底写库 + 异步发送失败消息，确保 MQ 发送成功 核心是「不能因为 MQ 挂了就丢数据」。发送失败先落库留痕，再由补偿任务重发；同时用 Confirm 机制拿到 Broker 的确认，没确认的进重试队列。
Gateway 统一路由 + 用户 ID 透传给下游 网关统一做鉴权和路由，解析出 userId 后放进请求头往下游传，下游服务直接从 Header 或拦截器里拿，不用每个服务再解析一遍 token，减少重复计算。

README 里的描述容易让人以为 Java 侧有个 SemanticChunker 类在运行时做切分。实际是：Java 侧没有分块逻辑，分块发生在离线入库阶段，脚本是 eval/ingest_docs.py（Python），而且严格说它是「递归字符切分」而不是「语义切分」——语义切分是按语义相似度找断点，我这里是按分隔符层级递归切。

话术：「分块是在离线入库脚本里做的，不在运行时。我用的策略是递归字符切分，按『二级标题 → 三级标题 → 段落 → 换行 → 句末标点 → 硬切』的优先级递归，chunk 512 字符、重叠 64 字符，重叠是为了防止关键句正好被切断在两个 chunk 的交界处。叫它语义切分不太准确，语义切分是按 embedding 相似度找段落边界——我现在的知识库是结构化 markdown，标题层级本来就是天然的语义边界，用标题切性价比更高。」

如果被问「为什么不直接用 SemanticChunker」：答「因为我的文档是带标题层级的 markdown，标题就是最可靠的语义边界，按标题切比按 embedding 相似度切更准也更便宜。如果知识源变成没有结构的纯文本，我才会考虑换成语义切分。」

但我也不是说自研就是对的——如果目标是两周内验证一个业务想法，我会直接用 Dify，然后只把关键链路自研。选型要看阶段。」

追问「那你觉得自研最大的代价是什么？」——答：可观测性和生态。自研要自己写日志、自己处理模型输出格式不稳的问题、自己维护重试降级；成熟平台这些是现成的。

A3这个项目如果流量涨 100 倍，哪里会先崩？

考点有没有架构层面的全局视角，而不只是会写功能。这题几乎是「能不能扛高并发」的通用考点。

话术「我会按顺序看四处。

第一是向量检索。现在 searchSimilar 每次请求都实时调 DashScope 做 query 向量化，这是个外部 API 调用，会成为延迟瓶颈也是成本大头。优化方向是 query embedding 缓存，或者换成本地部署的小 embedding 模型。

第二是 LLM 调用。所有请求共享模型服务的配额和连接，要加限流和熔断，否则上游抖动会直接把线程池打满。同时 ReAct 循环是同步阻塞的，请求线程一直被占用，并发一高 Tomcat 线程池就撑不住——这里应该改成异步或虚拟线程。

第三是 pgvector。HNSW 索引在百万级以下很舒服，再往上要考虑分片或者引入专用向量库。

第四是数据库连接和外部搜索。抓网页的线程池是有界的，打满了就会排队超时，需要加降级：搜索不可用时直接跳过联网这一路，保证主干能出答案。」

追问「虚拟线程为什么适合这里？」——答：ReAct 循环和 LLM 调用都是「等 IO」的阻塞型任务，线程绝大部分时间在等待。虚拟线程的挂起成本极低，JDK 21 又正好是项目的基础版本，spring.threads.virtual.enabled=true 一行配置就能让 Tomcat 用上，对这类 IO 密集场景吞吐提升明显。但要注意：synchronized 块会 pin 住载体线程，要换成 ReentrantLock。

A4这个项目最难的地方是什么？

考点难度必须是技术性的，不能是「配环境很麻烦」。

话术「最难的是让 ReAct 循环在各种异常情况下都能稳定收敛。理想情况下模型会按我给的协议输出『思考 → 工具调用 → 观察』，但实际上模型会跑偏：JSON 格式不规范、该停的时候不停、工具返回空结果后继续空转。我做了几件事：

一是硬上限，maxSteps 取 Planner 决策和用户配置的较小值，保证最坏情况下也就多花两三轮的 token。

二是把『模型不调工具』定义成循环的正常出口，而不是异常。它不调，就说明它认为信息够了，直接输出。

三是整条链路外面套一层降级：ReAct 抛异常就退回一次性工具调用 + 标准生成，用户在极端情况下依然能拿到答案，只是工具用得没那么精细。

四是审计日志把每轮的思考、调用了哪个工具、耗时多少都打出来，出问题能定位到底是模型的问题还是我工具的问题。

后来复盘我觉得还有更好的做法：直接改用模型原生 tool calling，让协议由 SDK 保证，我只需要处理工具的实现，能省掉一大半格式解析和容错代码。当时用文本协议是为了换模型方便，但代价是引入了不稳定性——这个权衡我现在会重新算一遍。」

A5如果让你重做，你会改什么？

考点反思能力。这题是送分题，一定要提前准备，而且要给出有技术含量的、具体的改进，不要说「加更多功能」。

三个改进（挑一个讲深，其余作为补充）

① 工具调用协议换成原生 Function Calling。现在是文本三段式协议 + 自己解析 JSON，格式不稳时会静默降级成最终回答，问题很隐蔽。换成原生 tool calling 后由 SDK 保证协议，容错代码能删掉一大半。

② ReAct 中间过程做成流式状态推送。现在要走完所有工具调用才吐第一个字，首 token 延迟很高。改成每轮调完工具就往前端推一个 {stage: 'searching', tool: 'web_search'} 这样的事件，和聊天工具的体验一致，用户等待期间不至于面对空白。

③ 评测从 28 条扩到真实日志。现在的评测集是我自己标的，代表性有限。正确做法是把线上的真实提问按语义聚类，从每个簇里采样再人工标注，让测试集和真实分布一致。另外要把评测接进 CI，改检索参数跑一遍对比，防止改坏。

B 组 · Agent 与工具调用

B1说说 ReAct 是什么，你的实现和标准 ReAct 有什么区别？

考点知不知道自己实现的边界在哪，别把教科书概念和自己的代码混为一谈。

话术「ReAct 的核心是让模型交替做『推理』和『行动』：先思考当前信息够不够，不够就决定调什么工具，拿到工具结果（观察）之后再思考，直到判断信息足够再输出答案。相比让模型一次性回答，ReAct 的价值是把『要不要查资料』这件事交给模型在推理过程中动态决定，而不是在入口处写死。

我的实现有两个比较明显的偏离：

一是标准 ReAct 是严格串行的『思考 → 行动 → 观察 → 思考』，我做了扩展，每轮允许并行发起多个工具调用，因为一个提问经常同时需要内部知识和外部实时信息，串行调两个工具就是两倍的等待。代价是每轮的推理和观察是打包处理的，不是逐个工具单独迭代。

二是标准 ReAct 通常一路流式输出，我为了拿到结构化的观察结果，每轮用的是同步调用，所以只有最终答案才流给用户。这是我知道的取舍，改进方向是把中间过程做成状态事件推送。」

追问「ReAct 和 Function Calling 什么关系？」——答：不冲突，是正交的两件事。Function Calling 解决的是「模型怎么把『我要调哪个函数、传什么参数』结构化地表达出来」，ReAct 解决的是「调完之后要不要继续调、什么时候停」的控制循环。生产里最稳的做法是 ReAct 的控制循环 + 原生 Function Calling 的协议表达，也就是我上面说的改进方向。

B2Planner 的作用是什么？为什么不直接让模型自己决定？

考点对「多一次模型调用」的成本敏感度，以及分层设计意识。

话术「Planner 是一次轻量的前置决策：输出一段 JSON，明确回答『意图是什么、要不要查知识库、要不要联网、建议几轮、用什么查询词』。它和后面 ReAct 的区别是——Planner 只做一次性判断，不产生回答；ReAct 是真正干活的多轮循环。

为什么要有这一层，而不是让 ReAct 自己看着办？主要是为了省成本和控风险。如果直接进 ReAct，像『你好』这种完全不需要检索的问题，模型也可能先调一轮工具，白白多花一次往返的 token 和时间。Planner 先用一次便宜的调用（输出的 JSON 很短）判断出『不需要工具』，就能直接走标准生成，把整条工具链省掉。

另外 Planner 还有个隐含作用：它是规则的锚点。模型决策失败时我会退回关键词规则兜底——问题里出现『最新』『趋势』就走联网，出现『简历』『STAR』『面试』就查知识库。这样即使模型服务抖动，链路也不会瘫。」

追问「那多一次调用不是反而更慢？」——答：是的，这是一次明确的取舍。Planner 的输出很短（一百多 token 的 JSON），成本远低于一轮 ReAct；而且它带来的收益不只是省钱，还有「决策可审计」——我把 Planner 的决策单独记进日志，出问题能直接看到是它判错了还是 ReAct 执行错了。如果做极致优化，可以把 Planner 和意图识别合并成一次调用，或者用本地小模型替代。

B3你的工具是怎么注册给模型的？

考点细节，答不好会显得只是照抄教程。

话术「用 Spring AI 的注解式声明。SearchAgentTools 这个类里用 @Tool(name=..., description=...) 标注方法，参数上用 @ToolParam 说明含义和是否必填，然后通过 ChatClient...tools(searchAgentTools) 把整个对象注册进去，框架会自动把注解描述转成模型的工具定义。描述写得好不好直接决定模型会不会在正确的场景选中正确的工具，所以我把 description 写成了『适合什么场景』而不是『这个函数干什么』——比如 knowledge_search 写的是『适合查询简历写法、STAR、项目表达、面试话术等』，给模型明确的使用边界。」

追问「现在有几个工具？扩展成 20 个会有什么问题？」——答：现在两个。工具一多，最先出问题的是选择准确率，描述相近的工具会被选错，或者模型为了保险一次性调用一堆工具。这时候需要按场景分组、给 Planner 做工具子集的路由，而不是把全部工具都塞进一次请求——这也是 MCP 这类协议想解决的问题（工具多了要有发现和筛选机制）。

B4工具返回结果为空或者报错，你的链路会怎么走？

考点异常路径的设计，这是区分「写完功能就交」和「考虑过线上情况」的分水岭。

话术「分三层。

工具内部：知识库检索失败或没有结果，返回的是一段说明性文本而不是抛异常——比如『知识库暂无匹配结果』。这样模型拿到的是一个它看得懂的观察结果，可以据此决定换个查询词再试，或者直接告诉用户知识库里没有。

网页抓取：单个页面超时 7 秒或抛异常，用 completeOnTimeout 和 exceptionally 返回一条内容为空的结果。链路继续走，最终拼提示词时跳过正文为空的结果——一个页面挂掉不影响其他页面。

整条工具链：如果 ReAct 循环本身抛异常（比如模型服务不可用），外层 onErrorResume 会捕获，记录降级日志，然后退回「一次性工具调用 + 标准生成」。再往上，如果连工具开关都是关的，就走纯生成。

所以整个链路的保证是：只要模型服务还在，用户就一定能拿到回答，只是用不用得上检索的区别。这个兜底逻辑是我特意设计的，因为工具调用引入的外部依赖太多了——搜索服务、网页、向量库都可能挂。」

C 组 · RAG 与向量检索

C1完整讲一下你的 RAG 链路。

考点能不能把 RAG 讲成一条工程链路，而不是「向量库查一下塞进 prompt」。

话术按「离线入库 → 在线检索」两段讲，见 3.4 的流程图。重点强调四个「为什么」：为什么切分、为什么双路、为什么重排、为什么截断。

「离线侧：文档按标题层级递归切分成 512 字符的 chunk、重叠 64，调 DashScope 的 text-embedding-v2 得到 1536 维向量，写进 PostgreSQL 的 pgvector 列，建 HNSW 余弦索引。

在线侧：用户问题进来，我用两路查询——一路是原始问题，另一路在问题后面拼一段导向语，把检索方向往『答案应该长什么样』偏。两路各取一半候选，按 id 去重合并，这一步会召回 topK 的两倍（expandFactor=2），是故意放大的。然后把候选交给 GTE 重排模型做精排，最后按 0.35 的相似度阈值过滤、最多保留 8 条，格式化成带相关度和分类的片段清单注入 system prompt。

注入的时候我会明确写一句『请优先据此组织回答，勿虚构知识库中不存在的事实』——这句话对压制幻觉很有用，它给了模型一个明确的拒答许可。」

C2为什么要做分块（chunking）？512 和 64 是怎么定的？

考点你知不知道分块是在解决什么问题。

话术「不分块的问题很直接：一整篇文档压成一个向量，语义被平均掉了。一篇讲简历的文档里包含排版、STAR、技能描述好几块内容，合成一个向量之后，用户问『STAR 怎么写』和问『技能栏怎么排』算出来的相似度几乎一样，检索就没有区分度了。反过来，如果切得太碎，一个 chunk 只有一句话，又缺上下文，模型拿到也理解不了。

所以分块本质是在『语义聚焦』和『上下文完整』之间找平衡点。

512 字符是我的知识源（结构化 markdown）下一个二级标题能覆盖的典型长度——按标题切出来的段落自然落在这个量级，所以 512 是一个跟着数据走的选择，不是拍的。64 字符的重叠是为了防止关键句正好被切在边界上，两边的 chunk 都能看到完整的那句话，代价是存储和 embedding 成本增加约 12%。

追问「怎么验证分块有效？」——答：这是我觉得做得最扎实的一步。我写了入库脚本支持 --mode whole（整篇入库）和 --mode chunk（切分入库）两种模式，用同一套 28 条评测集各跑一遍，比 Hit@K 和 MRR 的差值。这样「分块有没有用」是一个可复现的实验结论，不是感觉。

C3余弦相似度、内积、欧氏距离有什么区别？你用的哪个？

考点基础功，答错会很难看。

话术「三个的区别在对『长度』的敏感度上。

  • 内积同时受方向和长度影响，向量模长越大结果越大；
  • 欧氏距离看的是空间里的直线距离，同样被长度影响；
  • 余弦相似度只看夹角，把模长归一化掉了，衡量的是方向上的接近程度。

我用的是余弦距离（pgvector 的 <=> 算子），索引也是 vector_cosine_ops。原因是文本 embedding 的语义主要由方向表达，长度往往反映的是文本长短这类无关因素，用余弦能避免『长文本因为向量模长大而被误判为更相关』。

有个细节：<=> 返回的是距离（1 − cosθ，范围 [0,2]），而我要的是相似度，所以做了 similarity = 1 − d / 2 的换算，展开就是 (1 + cosθ) / 2，把结果归一到 [0,1]，这样 0.35 这个阈值才是可解释的。

追问「那如果向量都做了 L2 归一化呢？」——答：归一化之后模长都是 1，内积就等于余弦相似度，两者等价，这时候用哪个都行，而且内积计算更快。DashScope 的 embedding 不保证归一化，所以我用余弦更稳妥。

C4重排（Rerank）和向量检索是什么关系？为什么两个都要？

考点双塔 vs 交叉编码器的区别。

话术「两者是粗排和精排的分工。

向量检索是双塔结构：query 和 document 是分别编码成向量再算距离的。好处是可以提前把所有文档的向量算好建索引，检索是近似最近邻查询，非常快；坏处是两者从头到尾没有交互，只能算一个粗粒度的『整体语义像不像』。

重排模型是交叉编码器：把 query 和每个候选文档拼在一起放进模型过一遍，能捕捉词级别的细粒度交互，所以排序准得多。代价是每算一个候选都要跑一次完整推理，很慢——如果知识库有一万条，用重排全量排序是不可接受的。

所以工程上的标准做法就是我这个组合：用向量检索做粗排，快速把一万里挑出十几条；再用重排对这十几条精排。这也是我把 expandFactor 设成 2 的原因——向量检索可能把正确的文档排在第 8 位，如果我 topK 只取 5，它就被截掉了，重排再准也救不回来。先放大到 10 条给重排留空间，重排完再截到 8 条。

追问「重排挂了怎么办？」——答：我做了降级，DashScope 调用失败或响应解析异常时退回按向量相似度排序。重排是「锦上添花」，不是「不可替代」，所以可以降级；这也是把重排放在一个独立 Service 里、用配置项 rag.rerank.enabled 可以整体开关的原因。

C5RAG 是怎么缓解幻觉的？能完全消除吗？

考点对 RAG 的期望值要清醒，说「完全解决」就是不懂。

话术「RAG 能缓解但不能消除幻觉。

它起作用的机制是：模型回答时会优先依据上下文里给它的内容，而不是完全靠参数里的记忆。所以当问题落在我知识库覆盖的领域（简历写法、STAR、面试话术）时，回答的事实性明显更好。

我在实现上做了四件事来加强这一点：一是阈值过滤，相似度低于 0.35 的片段不注入，宁可不给也不给噪声；二是条数上限，最多 8 条，避免上下文太长稀释注意力；三是显式约束，注入时明确写『勿虚构知识库中不存在的事实』；四是分类过滤，允许按 category 收窄检索范围，减少跨领域干扰。

但要说清楚三个它治不了的场景：知识库里根本没有答案时，模型还是可能顺着常识编；检索回来的是不相关内容时，反而会误导模型（这就是为什么阈值和重排很重要）；问题本身要求综合推理时，模型可能在拼接多个片段的过程中产生错误的推论。

所以我的判断是：RAG 是『让回答有据可依』，不是『保证正确』。要再往前走，得加引用溯源——让模型明确标出每句话来自哪个片段，这样用户能自己验证；我的片段格式化里已经带了相关度和分类，算是为引用做了一半准备。」

C6知识库怎么更新？新增文档要全量重算向量吗？

考点有没有考虑数据运维，而不只是一次性导入。

话术「不需要全量重算。我有三条路径：

单条更新：updateKnowledge 改内容时会重新对这个 chunk 做一次 embedding 再写回，其他条不受影响。

批量导入：importBatch 按 16 条一批并发向量化后写入。

向量回填：refillEmbeddings 专门处理历史数据——按 id 升序扫出 embedding IS NULL 的记录分批补齐，用 executeBatch 批量提交。这个接口是为了兼容『早期只存了文本没存向量』的数据，也能用于换 embedding 模型后的重建。

批量导入有个坑我处理了：DashScope 批量调用可能返回数量对不上（部分失败），所以我做了逐条重试——批量失败就降级成一条一条调，单条也失败就把这条标记为空向量跳过，不让一条坏数据把整批导入搞失败。

追问「换了 embedding 模型怎么办？」——答：维度变了就必须重建，因为旧向量和新向量不在同一个空间里，混着用检索结果会彻底乱掉。我的处理是：启动时从 pg_attribute 读列的维度，然后校验每次返回的向量维度和它一致，不一致直接跳过并打警告——这样至少不会静默写进去一堆错维度的数据。彻底的做法是加一个模型版本字段，双写两套向量，切换时重建索引。

D 组 · 流式与 SSE

D1SSE 和 WebSocket 你怎么选？为什么用 SSE？

考点技术选型的基本判断。

话术「选 SSE，因为我的场景是单向的、服务器推给客户端的流式文本，不需要客户端在同一连接上持续发消息。

  • SSE 是普通 HTTP，天然穿透代理和网关，浏览器原生支持 EventSource，还有自动重连；服务端在 Spring 里就是返回一个 Flux 配 produces = text/event-stream，非常轻。
  • WebSocket 是全双工的，会带来连接状态管理、心跳保活、横向扩展时的会话粘滞这些复杂度——而我完全用不到双向能力。

所以结论是：只要是单向推送就用 SSE，别为了『看起来更高级』上 WebSocket。」

追问「SSE 有什么坑？」——答：三个。一是浏览器对同域 SSE 连接数有限制（HTTP/1.1 下约 6 个），多标签页会互相占用，需要 HTTP/2 或者用 fetch 实现 SSE 来规避；二是中间层代理可能缓冲响应导致看起来不流式，要配 X-Accel-Buffering: no；三是断线重连会重新发起请求，如果不带 last-event-id 就会重复生成，要注意幂等。另外我前端用的是 fetch-event-source 而不是原生 EventSource，因为原生 API 不支持自定义请求头，而我的接口需要 POST 传参。

D2流式响应里怎么区分「推理过程」和「最终回答」？

考点细节，说明你真的处理过这个数据。

话术「我把输出包装成一个统一结构，两个字段：reasoning 和 v。映射的时候判断 message.getMetadata().get("reasoningContent") 有没有值——有就说明这一片是推理内容（推理模型会有这个字段），包装成 {reasoning: "..."}；否则就是正文，包装成 {v: "..."}。前端按字段分别渲染：推理内容放到可折叠的『思考过程』区域，正文走 markdown 渲染。

落库的时候我也是分开存的，t_chat_message 表里有独立的 reasoning_content 字段。这样重新打开历史会话，思考过程不会混进正文里造成排版混乱。」

D3用户在生成过程中刷新页面 / 关闭浏览器，会发生什么？

考点流式场景下的资源释放与数据一致性，是很实际的问题。

话术「前端断开连接时，Reactor 会发出 CANCEL 信号。我的处理是：

已经产出的内容落库。在 doFinally 里捕获 CANCEL，如果聚合到的内容非空，就把『用户消息 + 已生成的部分回答』一起写进去——这样用户重新进会话能看到已经生成的部分，而不是白丢。

一个字都没产出就不落库。如果用户在发起请求后立刻关掉页面，这时候数据库里写一条空回答只会污染会话列表，所以直接跳过。

防止重复落库用 AtomicBoolean.compareAndSet 做一次性开关，因为 doOnComplete 和 doFinally 在取消场景下存在竞态，不控制的话可能同一个会话写两遍。

另外在上层，wrapChatStream 也对 CANCEL 做了处理，会把这次运行标记为『取消』而不是『失败』落进审计日志——否则我的异常率统计里会混进大量用户主动取消，失真。」

E 组 · 工程化、部署与数据库

E1为什么向量库和业务库都用 PostgreSQL？

考点技术选型的成本收益分析。

话术「因为这个项目的规模用不上专用向量库。用 pgvector 的收益是：

  • 少一个组件。不用额外维护 Milvus / Qdrant 这样一套独立的存储，部署、备份、监控都省了——我整个后端就是 Compose 里四个容器。

E2Docker Compose 里服务启动顺序怎么保证的？

考点depends_on 的坑，很常见的面试题。

话术「depends_on 默认只保证容器启动顺序，不保证里面的服务真的就绪了。所以我在 postgres 上配了 healthcheck——pg_isready 每 10 秒探一次——然后 backend 的依赖写成 condition: service_healthy，等数据库真的能接受连接了才启动。不然后端会在一开始连接失败然后崩掉。

另外 postgres 那边我把建表脚本挂到了 /docker-entrypoint-initdb.d/ 目录下，编排文件里带序号前缀 01-、02- 控制执行顺序。要注意这个目录只在数据卷为空时执行一次，所以它不是迁移方案——真要改表结构得上 Flyway 或者 Liquibase。我现在是靠手工执行脚本，这在生产里是不可接受的，是个明确的待改进点。

还有一点：日志我挂载到了宿主机目录，这样容器重建日志不丢。密钥不在 compose 文件里写死，走根目录的 .env，而且 .env 是 gitignore 的。」

E3pgvector 的 HNSW 和 IVFFlat 怎么选？

考点向量索引的原理认知。

话术「两者都是近似最近邻索引，也就是牺牲一点召回率换查询速度。

  • IVFFlat 会先把向量聚成若干簇，查询时只扫最接近的几个簇。它需要先有数据再建索引（训练聚类中心），而且数据变化后需要重建才能保持效果。
  • HNSW 是分层的小世界图，查询时在图上贪心跳转。它不需要训练，插入数据是增量维护的，召回率和延迟通常都更好。

我选 HNSW，主要两个原因：一是知识库会持续增删改，IVFFlat 每次大改都要重建，运维成本高；二是它不需要训练，空表就能建索引，部署流程简单。代价是构建慢、内存占用更大（每个向量要多存图的边），在数据量不大的情况下这个代价完全能接受。」

追问「HNSW 有哪几个关键参数？」——答：主要是 m（每个节点的最大连接数，越大召回越高、内存越多）和 ef_construction（建索引时的候选队列大小，越大索引质量越好、构建越慢）。查询时还可以临时调 hnsw.ef_search 在召回率和延迟之间做权衡。

E4这个项目怎么排查线上问题？

考点可观测性意识，很多候选人完全没有这块。

话术「我做了三层：

一是请求级的链路日志。每次请求生成一个 requestId，从意图识别、上下文装配、Prompt 构建、Planner 决策，到 ReAct 的每一轮工具调用，每一步都记 step + 耗时 + 摘要，统一带 requestId 输出。出问题直接按 requestId 捞全过程，能看到是 Planner 判错了、检索没召回、还是模型跑偏了。

二是关键指标埋点。首 token 延迟、总耗时、输出字符数、推理字符数、是否触发降级、走的哪条工具模式——每次请求结束打一条汇总日志。这些指标能回答『变慢了没有』『降级率是不是涨了』这类问题。

三是日志分级落盘。用 Log4j2 把 application 和 error 分成两类文件，保留 30 天；同时做了一件事——把 SSE 连接断开产生的异常做了降噪处理，因为用户在流式过程中关页面是常态，这类异常会把 error 日志淹掉，掩盖真正的问题。

现在的短板是审计日志只落在日志文件里，没有落库，所以做不了聚合分析（比如按天统计降级率、按耗时分布看 P95）。要改进的话应该异步写到一张审计表或者打进时序库，再配 Grafana 看板。」

F 组 · Java 基础与并发（结合项目）

F1你的线程池是怎么配的？为什么要多个池？

考点不只是会传参，还要知道为什么要隔离。

话术「我按任务类型拆了两个池：httpRequestExecutor 专门发 HTTP 请求（IO 密集，线程大部分时间在等网络），resultProcessingExecutor 专门解析 HTML（CPU 密集）。

为什么要拆？如果共用一个池，一批慢的网页请求会把池里所有线程占住，后面就算有解析任务也排不进去——虽然解析很快，但被慢任务堵死了。这是典型的用线程池隔离来做故障隔离：一类任务的异常不会传染给另一类。这个问题叫『线程池饥饿』。

另外我用的是 Spring 的 ThreadPoolTaskExecutor，可以配核心线程数、最大线程数、队列容量、拒绝策略和 CallerRunsPolicy 这类自定义行为。在批量抓取里我其实还依赖了 CompletableFuture 的超时机制，单条任务 7 秒超时，所以即使线程被占住，链路整体也不会无限等。

追问「为什么不用 Executors.newFixedThreadPool？」——答：因为它的队列是无界的 LinkedBlockingQueue，任务会无限堆积，内存迟早爆掉，本质上和直接 new Thread 一样危险（只是把 OOM 从线程栈换到了队列）。阿里规约也明确要求手动 new ThreadPoolExecutor 并指定有界队列。我在第二个项目（AI 报告平台）里改造的就是这个问题。

F2CompletableFuture 的 allOf / completeOnTimeout / exceptionally 分别做什么？

考点异步编排的基本功，你的项目里正好用了这三个。

话术「在并发抓取里三个都用到了：

  • allOf：把 N 个独立任务的 future 聚合成一个，等全部完成。注意它返回的是 CompletableFuture<Void>，本身不带结果，结果要从原来的 future 列表里 join 出来——我是在 thenApplyAsync 里遍历原列表拿的。
  • completeOnTimeout：给单个任务加超时兜底。7 秒还没抓到就用一个备用的空结果把 future 完成，这样它算『成功』不算『失败』，allOf 不会被卡住。
  • exceptionally：异常兜底，把异常转成一个降级值，避免异常向上传播导致整个聚合失败。

这两个兜底的意义是：CompletableFuture 默认的行为是「一荣俱荣、一损俱损」——任何一个子任务抛异常，allOf 的结果就是异常，前面成功的都白做了。抓网页这种外部依赖极不稳定的场景，必须让每个子任务自己把失败消化掉，返回降级值，整体才不会因为一个页面挂了而全盘失败。」

追问「thenApply 和 thenApplyAsync 的区别？」——答：thenApply 在完成上一个任务的那个线程上执行，thenApplyAsync 会重新提交到一个线程池（不传参就用 ForkJoinPool，我传了 processingExecutor）。我这里必须用 Async 并指定线程池，否则 HTML 解析会跑在 HTTP 线程上，回到我以为已经避开的那个问题。

F3HashMap 什么条件下转红黑树？（高频基础题，结合你的项目说说）

考点基础知识。注意这题和智询工作台关系不大，答完基础后可以主动把它拉到项目上，显得不只会背书。

话术「两个条件同时满足：单条链表的长度达到 8，且整个 table 的容量不小于 64。如果容量不到 64，会先扩容而不是转树——因为容量小的时候哈希冲突多是因为桶太少，扩容比转树更划算。反向的，红黑树节点数降到 6 会退化回链表，中间留 7 这个缓冲是为了避免在 7、8 之间反复转换。

阈值定成 8 是基于泊松分布的：哈希分布均匀的情况下，一个桶里出现 8 个元素的概率约为千万分之六，几乎不可能——所以正常情况下根本走不到树化，树化是一个防御极端情况的兜底。

结合项目说一句：我在做 RAG 双路召回合并的时候用了 LinkedHashMap 按 id 去重，选它而不是 HashMap 是因为要保留插入顺序——第一路检索的结果更贴近原始问题，去重时应该优先保留它并排在前面，而 putIfAbsent 只能保证不覆盖，顺序要额外处理，所以顺序敏感的合并就得用 LinkedHashMap。」

F4JVM 内存结构讲一下，你的项目里可能在哪出问题？

考点基础 + 结合项目。后半句才是分水岭。

话术先说结构：线程共享的堆和方法区（元空间），线程私有的虚拟机栈、本地方法栈、程序计数器。堆又分新生代（Eden + 两个 Survivor，默认 8:1:1）和老年代。对象优先在 Eden 分配，经历一次 Minor GC 存活就进 Survivor 并且年龄加一，年龄到 15（默认 MaxTenuringThreshold）或者 Survivor 里同年龄对象超过一半（动态年龄判定）就晋升老年代。大对象直接进老年代。

结合我的项目，最可能出堆内存问题的地方有三个：

  • 简历解析。PDFBox 和 POI 解析文件时会创建大量临时对象，文件本身还有 3MB 的限制——这个限制除了防滥用，也是在控制解析过程的内存峰值。
  • 流式聚合。落库的 Advisor 里用 StringBuilder 把整段回答聚合起来，长回答会一直待在堆上直到请求结束。这是必要的（不然没法落库），但意味着单个请求的内存占用和输出长度成正比。
  • 网页正文抓取。抓回来的原始 HTML 可能有几百 KB，如果并发抓取的条数或线程池配置不当，同时驻留的 HTML 会把堆压得很紧——这也是我把结果条数限制在前 5 条的原因之一。

排查思路是：先 jstat -gcutil 看是不是频繁 Full GC，jmap -histo 看对象分布找出异常增长的类型，必要时 jmap -dump 下来用 MAT 分析引用链。我现在没有配 JVM 参数，生产上应该至少设置 -Xms / -Xmx、选 G1 收集器并配上 OOM 时自动 dump。」

G 组 · 结合校园社区项目（缓存与消息队列）

G1你的二级缓存是怎么设计的？本地缓存和 Redis 怎么保证一致？

考点多级缓存的一致性，这是最容易被问穿的地方。

话术「结构是 Caffeine（进程内）→ Redis（进程间）→ MySQL。读的时候先查本地，没有再查 Redis，最后回源 DB 并逐层回填。用户信息这类热点数据，本地命中后完全不需要走网络，这是响应时间从 7ms 降到 3ms 的主要原因。

一致性是二级缓存最麻烦的地方，因为本地缓存是每个实例私有的，一个实例改了数据，其他实例并不知道。我的处理是：

  • 写数据时先删 Redis、再写 DB，然后通过 RabbitMQ 广播（fanout）把失效消息推给所有实例，每个实例收到后清掉自己的本地缓存。
  • 为什么是延迟双删？因为存在这个时序：线程 A 删缓存后正在写库，线程 B 在这中间读到旧数据又回填进缓存。等 A 写完之后，缓存里就是脏数据了。所以在写库之后再延迟一小段时间做第二次删除，把可能被回填的脏数据清掉。延迟时间要大于一次『读 DB + 写缓存』的耗时。

说实话这套方案的强一致是做不到的——延迟双删也只能覆盖大部分情况。底层思路是：缓存只用于能容忍短时间不一致的场景（比如用户昵称、头像这类展示数据），涉及库存、余额这种强一致的必须绕过缓存走 DB。这个边界我是清楚并且刻意划的。」

追问「本地缓存的容量和过期怎么设？」——答：Caffeine 用 maximumSize 限制条数（防内存无上限增长）+ expireAfterWrite 设一个较短的过期时间作为兜底的兜底——即使 MQ 消息丢了，过期也能保证最终一致。这个『短过期』是我认为比延迟双删更可靠的一层保障。

G2缓存穿透、击穿、雪崩分别怎么解决？

考点八股高频题，答的时候尽量说自己项目里的具体数值和选择。

问题本质我的处理
穿透查一个数据库里也不存在的 key，缓存永远不命中，每次都打到 DB对查询结果为空的 key 也缓存一个空值，TTL 设短一些（比如 60 秒）。这样恶意请求会被缓存挡住。更彻底的做法是布隆过滤器，在入口就把不存在的 key 拦掉——但它有误判率，且删除数据麻烦，所以我先用空值缓存
击穿某个热点 key 恰好过期，瞬间大量请求同时回源热点 key 用互斥锁或逻辑过期：只有一个请求去回源，其他请求短暂等待或直接返回旧的过期数据。对用户信息这种场景，返回稍微旧一点的数据比让用户等更好
雪崩大量 key 在同一时刻集体过期，或者缓存服务整体挂掉过期时间加随机扰动（基础 TTL 上叠加一个随机区间），避免同时失效。另外本地缓存本身就是一层保护——Redis 整体不可用时，热点数据还能从 Caffeine 拿到，这是多级缓存额外的容错价值
G3「兜底写库 + 异步发送失败消息」具体是怎么做的？

考点消息可靠性，核心问题是「怎么保证消息不丢」。

话术「要保证不丢，得看三个环节：

生产者到 Broker：开启 Confirm 机制，Broker 收到消息会回调确认；没收到确认的消息失败重试。如果重试也失败，就把这条消息落库留痕，由后台补偿任务定时扫描重发——这就是『兜底写库』。为什么不能只靠内存重试？因为进程一重启，内存里的重试队列就没了。

Broker 自身：声明队列和消息都设为持久化，防止 Broker 重启丢消息。

Broker 到消费者：用手动 ACK，业务处理成功再确认；失败就 nack 或者不确认，让消息重新投递。业务侧必须做幂等——因为『处理成功但 ACK 丢了』会导致消息重投，重复消费是必然出现的，不是异常。

延迟消息是用死信队列 + TTL 实现的：消息先进一个带 TTL 的队列，到期后变成死信转到真正的消费队列，达到延迟投递的效果。RabbitMQ 没有原生的延迟队列，这是社区的标准做法（也可以用延迟插件，但会增加部署依赖）。」

H 组 · 软性问题

H1你怎么保证自己写的代码是对的？

考点质量意识。这题很多人答「多测试」，太空。

话术「分三层。

第一层是能自动跑的验证。RAG 这种效果型的功能最难验证，因为它没有『对/错』只有『好/差』。所以我把评测脚本化了——改任何检索参数，跑一遍就知道 Hit@K 和 MRR 是涨了还是跌了，还能和上一次的结果做差值对比。这让『优化』变成了可验证的动作。

第二层是边界和异常。我习惯先把失败路径列出来再写主流程：模型不按格式输出、工具返回空、外部接口超时、用户中途关页面、数据库写一半失败。这个项目的三级降级和流取消时的部分落库，都是这么设计出来的。

第三层是可观测。上线之后靠日志定位问题，所以我在每一步都埋了耗时和摘要。判断标准很简单：出问题的时候，我能不能只看日志就说清是哪一步、为什么错。如果不能，就说明埋点不够。

不足是我没有写单元测试。Convincing 的借口我说不出口——真实原因是这个项目功能迭代快、我在赶进度。但代价是明显的：改一处逻辑要手工回归。如果重来，我会至少给 RAG 的截断、双路去重、ReAct 的解析这几个纯逻辑方法补上单测，因为它们是纯函数、最好测、也最容易改坏。」

H2AI 相关的东西你是怎么学的？遇到不懂的技术怎么解决？

考点学习能力和方法，尤其 AI 领域没有成熟教程可抄。

话术「我的路径是先看官方文档和源码，再自己实现一遍，最后用数据验证。

比如 RAG，一开始我也只是知道『切分 → 向量化 → 检索 → 重排』这个概念链条，但真做的时候发现到处是选择：chunk 切多大、阈值定多少、要不要重排、重排后留几条。这些参数没有任何教程能给我答案，因为它们完全取决于我的数据。所以我就写了一个切分入库脚本，支持整篇入库和切分入库两种模式，跑了对比实验，用 Hit@K 和 MRR 决定。这个方法是我从这个项目里学到的最有价值的东西——效果型的问题,要用实验而不是直觉来回答。

日常我会用 Claude Code 这类工具辅助开发，但我的用法比较克制：让它帮我写重复性的样板代码、解释我看不懂的报错、Review 我写的 SQL，但涉及架构取舍和检索参数的部分我会自己想，因为这些必须理解原理才能调。我也踩过一次坑——早期完全依赖它生成的代码，结果 ReAct 的解析逻辑有隐藏 bug，排查了很久，从那之后这类核心逻辑我都坚持自己写自己测。」

H3你的职业规划是什么？为什么投这个岗位？

考点稳定性与方向一致。不要说「想学更多技术」，太虚。

话术（投 Java 后端时）「短期我想先把后端的基本功做扎实，特别是高并发和数据一致性这块——我做过缓存和消息队列，但都是单机规模，很想在真实的大流量场景里把这些东西的边界摸清楚。长期我对 AI 应用的工程化很有兴趣，我做过 Agent 编排和 RAG 的完整链路，发现这个方向和传统后端的结合点非常多：怎么把 LLM 调用这种高延迟、高不确定性、高成本的外部依赖，做成一个稳定可控的系统——这里面需要的还是后端那一套：限流熔断、异步化、可观测、降级兜底。所以我希望找一个既能做扎实的后端，又能接触到 AI 应用落地的环境。」

话术（投 AI 应用/AI 工程岗时）把重点往前移：「我想做 AI 应用的工程化落地。我理解这个岗位的核心不是调模型 API，而是把模型的不确定性包装成产品能用的确定性——我在智询工作台里做的就是这件事：三级降级、格式解析容错、Token 成本控制、效果量化评测。这些经验让我知道一个 AI 功能从 demo 到可用之间差的是什么。」

07通用回答模板

下面这些模板是骨架，把方括号里的内容换成你自己的就能用。重点是掌握结构，而不是背字。

模板一 · 项目介绍（万能结构）

【一句话定位】这是一个 [做什么] 的 [什么系统]，解决 [谁的什么痛点]。
【为什么难】这个场景的难点在于 [技术上真正的难点]。
【技术选型】后端用 [技术栈]，[关键选型] 是因为 [理由]。
【我的角色】我负责 [具体模块]，其中 [最有含金量的部分] 是我独立设计并实现的。
【做成什么样】[量化结果]，这个数字是通过 [评测方法] 得到的。

套用到智询工作台：

「这是一个 AI 简历优化与职业顾问平台，解决通用大模型在求职领域缺乏专业知识和实时信息的问题。难点在于要让模型自己判断该不该查资料、查不到怎么兜底，同时保证输出的稳定性和可控的成本。后端用 Spring Boot 3.4 + Spring AI 接 DeepSeek 和 DashScope，存储选了 PostgreSQL 加 pgvector，这样向量库和业务库能共用一套事务。我负责 Agent 编排链路和 RAG 检索链路的设计与实现，其中 ReAct 多轮工具调用和三级降级是我独立设计的。最终检索 Hit@5 做到 92.9%，Hit@10 100%，这是用 28 条标注测试集跑出来的可复现结果。」

模板二 · STAR 描述技术难点（不要讲产品，讲技术）

S（情境）：在做 [功能] 的时候，我发现 [具体的技术现象/问题]。
T（任务）：我需要在不 [不能牺牲的东西] 的前提下，解决 [这个问题]。
A（行动）：我做了三件事——
   ① [做法一]，因为 [原理层面的理由]；
   ② [做法二]，权衡是 [代价]，但我接受因为 [原因]；
   ③ [做法三]，这是兜底，保证 [最坏情况下也不会怎样]。
R（结果）：[量化结果]，并且 [可复现的验证方式]。

套用示例（RAG 效果不好）：

「S：知识库搭好之后我发现，用户问『我该不该在简历里放照片』，检索回来的却是讲排版规范的内容——字面上看问题在问照片，但知识库里对应的条目讲的是『简历不宜包含敏感信息』，措辞不重合，向量距离就拉不开。

T：我要在不动知识来源、不引入人工规则的前提下，把这类『问法和答案措辞不一致』的召回提上来。

A：我做了三件事。一是双路查询：除了用原始问题检索，再加一路在问题后面拼一段导向语，把查询向量往『答案该长什么样』的方向偏，本质是轻量的 query rewrite。二是扩大召回再精排：把候选放大到 topK 的两倍，交给 GTE 重排模型做交叉编码精排——因为向量检索是双塔结构，只能算粗粒度相似度，重排能把 query 和文档拼起来算，排序准得多。三是阈值截断：相似度低于 0.35 的片段宁可不给，因为给噪声比不给更糟，它会误导模型。

R：我用 28 条带标注的测试集做了评测，Hit@5 92.9%、Hit@10 100%、MRR 0.736、空结果率 0。这个结果可复现——我写了脚本支持两次实验做差值对比，改任何参数都能量化地知道是变好还是变坏。」

模板三 · 遇到的最大困难

【困难是什么】我遇到的最大困难是 [技术问题]，它的难点在于 [为什么难]。
【我一开始想错了】我最初的思路是 [错误方案]，跑出来 [失败现象]。
【怎么定位的】我先 [定位手段]，发现 [根因]，确认问题出在 [具体位置]。
【最终方案】所以我改成 [方案]，关键点是 [核心机制]。
【学到了什么】这件事让我意识到 [方法论层面的收获]。

套用示例（ReAct 循环不稳定）：

「困难：ReAct 循环在真实使用中不稳定，模型有时候会不按我给的格式输出，有时候该停的时候不停、一直重复调工具。

想错了：我一开始的解法是不断加长提示词里的格式说明，把 JSON 示例写得更详细。结果提示词越来越长，成本上去了，稳定性只提升了一点——因为模型输出的随机性不是靠写清楚就能完全消除的。

怎么定位：我开始记每一步的审计日志，把每轮的思考、解析出来的工具调用、耗时都打出来。看日志就清楚了：问题分两类——一类是 JSON 解析失败（格式问题），一类是模型在信息足够后继续调工具（收敛问题）。这两类的解法完全不同，混在一起时我根本分不清是哪种。

最终方案：分开处理。格式问题用兜底降级——解析失败不当作异常，而是让它走标准生成路径，保证用户一定有答案；收敛问题用硬上限——maxSteps 取 Planner 决策和用户配置的较小值，最坏情况下也就多花两三轮 token。

收获：我意识到不要把系统的稳定性寄托在提示词的措辞上，模型的行为是不可控的，稳定的做法是在外面套一层确定性的工程约束：上限、超时、降级、重试。后来我看到一句话印证了这个想法——LLM 应用的核心工作是『驯服不确定性』，我完全同意。」

模板四 · 为什么这么设计

【先给结论】我选 [方案] 而不是 [替代方案]，核心原因是 [一句话本质]。
【对比】如果用 [替代方案]，[会带来什么具体的坏处]。
【代价】我这个方案也不是没有代价：[代价是什么]。
【但我接受，因为】[为什么这个代价可以接受]。
【边界】如果 [某个条件变化]，我会换成 [另一方案]。

背下这个结构，任何「为什么用 X 不用 Y」都能套。面试官最欣赏的不是「X 更好」，而是你知道 X 的代价在哪、以及什么条件下会改用 Y——这说明你是在做判断，而不是在跟风。

模板五 · 你负责哪部分（个人项目的诚实版）

这个项目是我独立完成的，从前端到部署都是我一个人做。
不过如果按投入的比重算，主要精力在 [后端 Agent 编排和 RAG 这一块]，
大概占了 [70%]。[前端] 那一层我做到了 [可用]，但 [哪些方面不够好]——比如我
没做组件拆分，主页面文件比较长。

主动说一个自己的不足会比说「全都是我做的」更有可信度。面试官见过太多把教程项目说成自己独立设计的候选人，你主动划边界，反而说明你的自我认知是准的。

但注意：划边界要划在「做完了但做得不够好」的地方，不要划在「核心功能是别人的」上。核心链路必须是你做的，否则这个项目在面试里就没有意义。

模板六 · 完全不会时怎么答

不要沉默，不要硬编，不要含糊地说「大概是这样」。用这个三段式：

  1. 明确说不会：「这个我没有实际用过，不敢乱说。」
  2. 给出你知道的最近邻知识：「我的理解是……（讲你确实知道的相邻概念），但具体到这个点我不确定。」
  3. 给出你的推演：「如果让我现在判断，我会从……这个角度去想，但需要查一下验证。」

这个回答既诚实、又展示了你有解决问题的思路。面试官问的很多问题本来就不是要你会不会，而是想看你面对未知时的反应方式。

模板七 · 反问环节（一定要问）

技术类（推荐，显得你真的关心工作内容）：

  • 团队现在在做的 AI 应用，是更偏平台化（做能力给业务方用），还是直接面向终端用户？
  • 这块业务现在最大的技术瓶颈是什么——是模型效果、成本，还是工程稳定性？
  • 团队怎么做 AI 功能的效果评估？有没有类似评测集的机制？
  • 新人进来一般会先负责哪类模块？

成长类（显示你想长期干）：

  • 团队的代码评审和技术分享是怎么做的？
  • 新人有没有 mentor 机制？

不要问：「加班多不多」（可以问「团队的工作节奏大概是怎样的」，一样能拿到信息）；「我表现怎么样」（当场问这个很尴尬）；官网上能查到的信息。

08面试前 48 小时清单

必须搞清楚的知识点

  • ReAct 和 Function Calling 的区别
  • 双塔 vs 交叉编码器，为什么先粗排再精排
  • 余弦距离 / 内积 / 欧氏距离的区别
  • <=> 算子和 1 − d/2 的换算
  • HNSW vs IVFFlat
  • SSE vs WebSocket
  • 线程池为什么不用 Executors 工厂方法
  • CompletableFuture 三个兜底方法的语义
  • HashMap 树化条件（8 + 64）
  • JVM 内存结构与对象晋升
  • 缓存穿透 / 击穿 / 雪崩
  • 延迟双删的时序图

必须能张口就来的数字

  • 评测集 28 条
  • Hit@5 92.9% / Hit@10 100%
  • MRR 0.736 / 空结果率 0
  • 相似度阈值 0.35，最多保留 8 条
  • 召回放大系数 2
  • chunk 512 字符 / 重叠 64 字符
  • embedding 维度 1536，批量 16
  • ReAct 默认最多 3 轮
  • 历史消息加载 50 条
  • 抓取超时 7 秒，取前 5 条结果
  • 简历上传限制 3MB
  • 日志保留 30 天

必须处理掉的四处简历风险

  1. MCP —— 代码里零命中，删除或准备 5.1 的话术
  2. 分块位置 —— 是离线 Python 脚本，不是 Java 运行时
  3. 正文清洗 —— 是 Jsoup 抽纯文本 + 条数限制，不是「三层清洗」
  4. 70% 这个数字 —— 口径改成「字符量降幅 90% 以上，对外保守说约 70%」

最后一件重要的事

面试前，把项目完整跑一遍。不是看代码，是把 docker compose up -d --build 跑起来，打开页面，自己问几个问题，看日志里打出来的每一步。真跑过一遍的人和一个只看过代码的人，讲出来的东西质感完全不同——你会自然地提到「这里提示词会慢一点」「这个工具偶尔返回空」，这些细节是背不出来的。

如果时间允许，把那 28 条评测跑一遍，看到真实的 Hit@K 数字出现在自己屏幕上的时候，你讲这组数据时的底气是不一样的。

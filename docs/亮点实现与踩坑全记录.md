## 2. 亮点实现细节

以下每条都是"我给你的方案里的亮点"在本项目的**具体落点**。

### H1｜受控 Planner + 三模式编排（ReAct / Fallback / Standard）

**目标**：既要有 Agent 的灵活性，又不能让模型"放飞"——所有工具调用受策略约束，且任何一环失败都有降级路径。

**实现位置**：`AgentOrchestratorImpl` + `AgentPlannerServiceImpl`

**编排主干**（`AgentOrchestratorImpl`）：

```
streamChat(reqVO)
 ├─ runFoundationSteps()           # 固定多步：IntentClassifier → ContextAssembler → PromptBuilder
 ├─ runPlanner()                   # 模型 JSON 决策，失败退规则兜底
 └─ 按决策分流：
     ├─ streamChatWithNativeTools()  # 原生工具调用模式
     ├─ reactLoop()                  # ReAct：多轮、每轮可并行多工具
     ├─ streamChatWithFallbackLoop() # ReAct 异常 → 一次性工具调用
     └─ streamChatStandard()         # 不调工具，直接生成（最终兜底）
```

**Planner 的产物**（`PlannerDecision`）：`intent / needKnowledgeSearch / needWebSearch / maxReactSteps / toolStrategy`。提示词强制"只输出 JSON，不要 markdown/解释/代码块"，解析失败走关键词规则兜底（`AgentPlannerServiceImpl`）。

**ReAct 协议**（`buildReactPrompt`）关键设计——**用显式文本协议而非 function call**：

```
思考：<推理过程>
工具调用：[{"tool":"knowledge_search","args":{...}}, {"tool":"web_search","args":{...}}]
最终回答：<答案>
```

- 每轮模型可**同时调用多个工具**（`extractToolCalls` 解 JSON 数组）；
- 解析出的 observation 追加进 `reactTrace`，下一轮拼进 prompt（`## 历史工具调用轨迹`）；
- 模型输出 `最终回答：` 即结束循环。

**为什么不用原生 function call？**
- 需要兼容的模型（deepseek-flash）function call 稳定性不如显式文本协议；
- 文本协议便于**把 ReAct 轨迹直接落审计日志**，可回放；
- 代价是要自己写解析器，且模型不听话时要有兜底（`extractThought` 在找不到"思考："时截前 100 字符兜底）。

> 面试点：这里能讲清"为什么选文本协议而不是 FC"，以及"协议是模型无关的"这一权衡。

### H2｜固定多步编排 + 统一 AgentContext

**目标**：把"意图 → 上下文 → 提示词"做成可测试的固定步骤，而不是散落在一个大方法里。

**实现**：`AgentStep` 接口 + 三个 `@Component` 实现：

| Step | 行为 |
|------|------|
| `IntentClassifierStep` | 简历场景直接定意图；否则关键词规则（面试/职业/简历/offer）分类 |
| `ContextAssemblerStep` | `knowledgeRag=false` 直接置空并短路；否则按场景调用 chat / resume 两套 RAG context 构建 |
| `PromptBuilderStep` | 按 `AgentScene` 分支构建 system prompt |

`AgentContext` 是**贯穿全链路的可变载体**：requestId、scene、intent、ragContext、reactTrace、toolMode、startedAtMs……审计日志只需读它。

**踩点**：`ContextAssemblerStep` 在 `knowledgeRag=false` 时**必须短路返回**，否则会白跑一次向量检索——这是"开关要对每一层都生效"的典型细节。

---

### H3｜双路检索（语义 + 输出锚点）+ 去重合并 + 扩大召回

**目标**：单路向量召回对"答案型问题"覆盖不足，用第二路"带回答方向的 query"补召回。

**实现位置**：`ResumeKnowledgeRagServiceImpl`（Java）与 `python-ai/app/services/retrieval.py`（Python，语义完全对齐）

```
q1 = 原始语义
q2 = 原始语义 + 输出锚点（引导偏向回答方向）

例：
  CHAT  锚点 → "（请从简历撰写、面试表达、职业发展、量化成果等角度补充相关条目）"
  RESUME 锚点 → "（请从简历结构、STAR、项目描述、技能关键词、面试话术等角度补充相关条目）"

两路各召回 perQuery 条 → 按 id 去重（**q1 优先**）→ 合并候选池
```

**扩大召回**：`expandK = topK × expandFactor(2)`，每路取 `expandK` 的一半（至少 2），给重排留候选空间。

**踩点与思考**：
- **"输出锚点"是双刃剑**：它确实提升了答案型 query 的召回，但相当于人为改写了 query 语义，会引入偏噪的候选。所以必须靠**重排 + 阈值截断**在下游把噪声刷掉——也就是说 H3 和 H4 是**成对设计**的，不能只上 H3。
- **去重谁优先**：q1 是用户真实语义，q2 是加工过的，所以 `LinkedHashMap` 保序、q1 覆盖 q2。这个顺序影响重排后的 top1，是个容易被忽略的细节。
- 简历正文进检索前**截断到 2000 字符**（Java/Python 两侧一致），避免长文把 query 语义带偏、也省 embedding 成本。

### H4｜重排 + effectiveScore + 阈值截断 + 三级降级

**目标**：向量分数只保证"语义邻近"，不保证"回答相关"；重排把相关度拉回来；且重排是外部 HTTP，**绝不能让它的失败中断整条 RAG**。

**三级降级链**：

```
rerank.enabled=false        → 直接用向量分排序
rerank HTTP/解析/超时异常   → 记 warn，退化为向量分排序
rerank 成功                 → rerank_score 作为 effectiveScore
```

**统一分数抽象**（Java `RankedDocument` / Python `RankedDocument`）：

```java
public double effectiveScore() {
    if (rerankScore != null) return rerankScore;  // 重排优先
    if (vectorScore != null) return vectorScore;  // 退化
    return 0.0;
}
```

**阈值截断**（`RagTruncationService`）：`similarity-threshold=0.35`，`max-top-k=8`；按降序遍历，分数达标才留，够 8 条即停。

**为什么阈值取 0.35？** 不是拍脑袋——从 §1.2 的用例数据看，命中条的 top1 相似度普遍落在 0.71–0.86，而未命中/弱相关的尾部片段大多 < 0.6。0.35 是一条"宁可少给、不可给错"的保守线，配合 `maxTopK=8` 双重兜底，防止把弱相关片段塞进 prompt 污染生成。

**踩点**：`effectiveScore` 这套抽象是**跨语言复用的核心契约**——Java 和 Python 两份实现必须给出同样的分数语义，否则同一份 query 在两边召回结果不一致（见 H10）。

### H5｜Chunk 切分策略（512 / 64 / 递归分隔符）

**目标**：整篇文档入库会导致"一条记录语义模糊"，切碎又丢上下文。

**实现**：`eval/ingest_docs.py` 支持两种模式做对照实验：

| 模式 | 行为 |
|------|------|
| `--mode whole` | 整篇文档一条记录（baseline） |
| `--mode chunk` | 递归字符切分后入库（推荐） |

**切分参数**：分隔符优先级 `## → ### → 段落 → 换行 → 句末标点 → 硬切`，`chunk_size=512`，`overlap=64`；README 补充最短 100（过短合并）、最长 1024（强制切）。

**数据源**：`docs/knowledge/*.md`（3 篇：简历结构与排版、STAR 与项目经历、Java 后端八股）。

**踩点**：
- **overlap 的必要性**：512 硬切会把一个完整论点劈成两半，64 字符重叠让"跨块语义"至少在一侧完整出现。
- **分隔符优先级**：优先按 `##` 标题切，能让每个 chunk 尽量是"一个自洽的小节"，比纯按字符数切语义完整得多。
- **对照实验必须留产物**：`--mode whole` vs `--mode chunk` 就是为了产出 §1.2 那张表——但当前只存了 chunked 一份，这是缺口。

### H6｜联网搜索三层正文清洗

**目标**：搜索结果页里 80% 是广告/导航/页脚，直接塞进 prompt 既污染又烧 token。

**实现**：`SearXNGServiceImpl`（聚合搜索）+ `SearchResultContentFetcherServiceImpl`（正文抽取）

```
用户问题 → SearXNG JSON 接口 → 按 score 降序取前 N 条
        → OkHttp 并发抓取结果页（CompletableFuture + ThreadPoolTaskExecutor）
        → Jsoup 三层清洗：
            ① 正文识别：取 article/main，丢 nav/footer/ad
            ② 结构化清洗：保留 h1-h3/ul/ol/pre/code，过滤 Cookie 等模板文本
            ③ 智能截取：前 3000 字符，段落边界截断
        → 注入 prompt
```

**踩点**：
- **搜索引擎列表是按本地网络可达性挑的**（`_SEARXNG_ENGINES` 里塞了 wolframalpha / mojeek / bing / 360search 等），说明通用引擎在本地经常超时，必须挑一批活的。
- **任何失败必须兜底返回空**：SearXNG 没启动、超时、HTML 解析异常，全部 `catch` 后返回空列表，绝不上抛——联网搜索是**增强项**，不能因为它是可选能力就把主链路搞挂。
- **并发抓取要做上限**：10 条结果并发抓正文，线程池 + 超时必须配，否则一个慢站点拖垮整轮。

### H7｜SSE 流式 + 记忆注入 + 流式落库

**三段式工程化**：

1. **记忆注入**（`CustomChatMemoryAdvisor`）：请求前从 `t_chat_message` 按 `chatId` 加载近期消息，转成 Spring AI `Message` 列表注入本次请求，实现多轮上下文。
2. **流式输出**：统一封装成 `AIResponse` / SSE `data:{"v":"片段"}`，前端 `fetch-event-source` 逐帧拼接渲染。
3. **流式落库**（`CustomStreamLoggerAndMessage2DBAdvisor`）：流式过程中累积内容，流结束（含异常/取消）时把 assistant 消息写库；用 `TransactionTemplate` 保证一致。

**踩点**：
- **流式 + 落库的取消处理是最容易漏的**：用户在浏览器中途关闭/刷新，Reactor 会触发 cancel 而不是正常 complete，若不监听（`SignalType` / `doOnCancel`）就会**丢消息或写半截**。
- **落库要幂等**：用 `AtomicBoolean finished` 之类的标志防止 complete 和 cancel 双触发重复写。
- **Python 侧对齐 SSE 协议**：`python-ai/app/api/chat.py` 明确"每帧 `data:{"v":"..."}`，`ensure_ascii=False` 保证中文不转义转成 `\uXXXX`"，前端零改动即可切换后端——这是**接口契约先行**的价值。

### H8｜Agent 审计日志（requestId 全链串联）

**实现**：`AgentAuditLogger`

```
recordRunStart    → 生成/复用 requestId，记录 scene / knowledgeRag / networkSearch /
                    searchToolEnabled / maxAgentSteps / startedAtMs
recordToolMode    → 记录最终落到 native / react / fallback / standard / resume-direct 哪条路
recordFallback    → 记录降级原因（异常）
finishRun         → 记录成功/失败 + 总耗时
```

**为什么这个重要**：Agent 系统最痛的是"线上回答问题，你根本不知道它走了哪条路、调了几次工具、为什么慢"。一个 requestId 把 Planner 决策、工具轨迹、最终模式、耗时全串起来，**这是"能做线上排障"和"只能本地 debug"的分界线**。

**面试点**：可以讲"我把 toolMode 记为枚举而非布尔，因为降级路径有 5 条，只有区分开才能统计各路径占比、发现 ReAct 是不是经常在退化为 fallback"。

### H9｜评测闭环三件套（造集 → 检索评估 → 端到端裁判）

这是整个项目**最值钱的工程能力**，也是"简历优化 demo"和"可量化系统"的分水岭。

**① 造集** `eval/build_dataset.py`
```
分页拉全量知识 → 每条用 DeepSeek 生成 N 个"用户会问、且该条能回答"的中文问题
→ dataset.jsonl: {"question", "expected_id", "category"}
```

**② 检索离线评估** `eval/retrieval_eval.py`
```
对每个 question 调 POST /resume-kb/search（topK=10）
→ 计算 Hit@1/3/5/10、MRR、平均 top1 相似度、空结果率
→ 控制台报告 + JSON 落 eval/results/retrieval_{label}_{timestamp}.json
→ 支持 --compare 两个结果文件对比
```

**③ 端到端裁判** `eval/e2e_judge_eval.py`
```
调后端 SSE 接口拿完整回答 → DeepSeek 裁判按 accuracy/completeness/relevance 打 1-5 分
→ 支持 --rag on/off 对比有 RAG / 无 RAG
```

**踩点与思考（重点）**：
- **"用 LLM 造测试集"的最大陷阱是措辞泄漏**：让模型"看着某条知识生成问题"，它很容易把原文关键词抄进问题里 → 检索自然命中 → 指标虚高。缓解手段：提示词要求"口语化、角度不同"，且最好人工抽检 + 加一批"跨条目/不可答"的负样本。
- **单指标不够**：Hit@K 看"能不能召回到"，MRR 看"排得靠不靠前"，两者要一起看。本项目 Hit@1=0.61 但 Hit@5=0.93，说明**召回能力够、排序能力还有优化空间**——这正好指向 Rerank 的收益点。
- **`--compare` 是设计亮点**：评测工具本身支持双结果 diff，才能支撑"改一版、量一版"的迭代闭环，而不是跑完就忘。

### H10｜Java / Python 双栈对照实现（同一检索语义，两套实现）

**定位**：Java 主站负责业务（会话、简历、知识库 CRUD、SSE、落库），Python 服务负责 AI 链路（检索/重排/嵌入/**Agent**）。两边**语义完全对齐**。

对齐点（`retrieval.py` 文件头明确写了对齐目标）：

| 契约 | Java | Python |
|------|------|--------|
| 双路 query + 锚点 | `ResumeKnowledgeRagServiceImpl` | `retrieval.py` |
| 去重（q1 优先） | `LinkedHashMap` | 同语义 |
| `effectiveScore` | `RankedDocument` | `RankedDocument` |
| 阈值/条数 | `0.35 / 8` | `0.35 / 8` |
| SSE 帧格式 | `{"v": "..."}` | `{"v": "..."}` |
| 响应包装 | `{success,data,message}` | `{success,data,message}` |

**踩点**：跨语言对齐最大的坑是**"看起来一样，实际不一样"**——比如 Java 用 `<=>` 余弦距离、Python 也用 `<=>`，但如果一方的 embedding 列是 `text` 一方是 `vector`，或者一方 cast 了 `::vector` 一方没 cast，结果会静默偏差。解决方案是**把 SQL 语义显式写死并加注释**（见 P5），并且**用同一份 eval 数据集在两边各跑一次比对**。

## 3. 踩坑与思考过程

格式：**现象 → 定位 → 权衡 → 结论**。以下都是从这个仓库的代码/注释/配置里能直接读出来的真实坑。

### P1｜pgvector 表被建到了 `public`，而不是 `cv`

- **现象**：连 `?currentSchema=cv,public`，但建表后 `cv` 下找不到表，检索空结果。
- **定位**：`currentSchema` 只影响 JDBC 连接的默认 schema，**建表脚本执行时的 `search_path` 另说**；`CREATE SCHEMA cv` 若不存在，`SET search_path TO cv, public` 里的 `cv` 会被静默忽略，表就落到 `public`。
- **权衡**：是靠应用层开关，还是脚本兜底？→ 脚本更可靠。
- **结论**：`schema-all.sql` 开头强制 `CREATE SCHEMA IF NOT EXISTS cv; SET search_path TO cv, public;`，并在注释里写明"否则 cv 会被忽略，表会误建到 public"。**一个静默失败，代价可能是几小时排查。**

### P2｜重排端点路径不一致，导致静默降级

- **现象**：Java 侧重排"总是失败"，但日志只有 warn，检索仍返回（按向量分），很难察觉 Rerank 根本没生效。
- **定位**：Java 用的是简写 `/api/v1/services/rerank`，而 DashScope 官方全路径是 `/api/v1/services/rerank/text-rerank/text-rerank`。Python 侧用的是全路径。
- **权衡**：改代码 vs 改配置？→ 端点必须走配置，但默认值要是全路径。
- **结论**：`rerank.py` 注释显式标注"Java 侧使用简写…此处对齐官方完整路径"。**更大的教训**：降级机制会掩盖配置错误——**降级必须打 warn/error 并可被审计日志统计**，否则"看起来能用"其实是"一直在退"。

### P3｜外部依赖失败绝不能中断主链路

- **现象**：重排/联网任一失败，整个回答 500。
- **结论**：确立"外部能力 = 可选增强"原则：
  - 重排失败 → 退向量排序（`DashScopeRerankServiceImpl` / `rerank.py`）
  - 联网失败 → 返回空列表（`SearXNGServiceImpl` / `search.py`）
  - Planner 失败 → 规则兜底（`AgentPlannerServiceImpl`）
  - ReAct 失败 → fallback 循环（`AgentOrchestratorImpl`）
  - Python 服务 DB 不可用 → 不阻断启动，只 warn（`main.py` lifespan）

### P4｜Embedding 批量上限与"条数守恒"

- **现象**：一次塞太多文本给 DashScope embedding 会被限流/截断，导致**输入 N 条、输出不到 N 个向量**，后续 `zip(valid, vectors)` 静默错位，向量和内容对不上。
- **结论**：`EMBED_BATCH_SIZE = 16`（官方上限 25，留安全余量）；**批量失败逐条重试**，尽量保证条数守恒；**维度不符显式抛 `EmbeddingError`**，宁可失败也不要写入错位数据。

### P5｜pgvector 的 embedding 列类型不确定

- **现象**：有的环境列是 `vector(1536)`，有的是 `text`（历史数据），SQL 里写死 `::vector` 会报错，不写又查不了。
- **结论**：`pg.py` 启动时**探测列元数据**（类型分类 / 维度 / cast 类型全名）并缓存，写 SQL 时按探测结果动态 cast。**这体现了"迁移/多环境场景下不要假设 schema 稳定"。**

### P6｜Python 同步驱动在 async 里阻塞事件循环

- **现象**：`psycopg` 是同步的，直接在 FastAPI 的 `async` 路由里调用会**阻塞事件循环**，并发一上来就全卡住。
- **结论**：DB 调用放 `asyncio.to_thread` 执行（`kb.py` 注释"数据库为同步驱动，放线程池执行"）。**没有为了 async 而硬换 asyncpg**——因为要复用和 Java 完全一致的 SQL 语义，换驱动风险更大。这是一个典型的**"性能 vs 一致性"权衡**。

### P7｜流式 + 落库的取消/异常一致性

- **现象**：用户中途关页面，消息丢失或只写了半截助手回复。
- **结论**：Advisor 里监听 `SignalType`（complete/cancel/error），用幂等标志位 + `TransactionTemplate` 保证"每个请求恰好落一条 user + 一条 assistant"。见 H7。

### P8｜Windows 上 SSE 断开的 ERROR 噪声

- **现象**：浏览器主动断开 SSE，Tomcat 往已关闭连接写数据抛 `IOException`（Windows 文案："你的主机中的软件中止了一个已建立的连接"），`dispatcherServlet` 打 ERROR，日志红一片，排障被严重干扰。
- **结论**：`log4j2.xml` 加过滤器把"客户端中止"类异常降噪，**不影响真正的服务端异常**。注释写得很清楚，说明是被这个问题折磨过的。

### P9｜`useRag=false` 的逐层短路

- **现象**：关了知识库，但还是慢/还是带了知识内容。
- **结论**：开关必须在**每一层**生效——`ContextAssemblerStep` 里 `knowledgeRag=false` 直接置空返回（P2 同类：**开关要有短路，不能只改展示层**）。

### P10｜双路检索的"输出锚点"引入噪声

见 H3 踩点：锚点改写 query 语义 → 必须靠 H4 的重排 + 阈值在下游清洗。**教训：增强手段要配对应的抑制手段，不能只加不减。**

### P11｜阈值 0.35 的依据

见 H4 踩点：用真实相似度分布反推，而非拍脑袋。**面试时能说出"我是从数据分布里选的阈值"就赢了大部分人。**

### P12｜LLM 造测试集的"措辞泄漏"

见 H9 踩点：造集时模型抄原文关键词 → 指标虚高。缓解：口语化要求 + 人工抽检 + 负样本。

### P13｜CORS 端口不一致

- **现象**：本地前端跑 5173，后端 `@CrossOrigin` 写死 `http://localhost:5174`，跨域失败。
- **结论**：README 明确提示"本地联调让前端端口匹配或按需调整跨域配置"。**小坑，但把新人卡住半小时。**

### P14｜Spring AI 的 pgvector 自动配置与手写 SQL 冲突

- **现象**：`spring-ai-starter-vector-store-pgvector` 会自动建表/初始化，而项目是**手写 SQL + `currentSchema=cv`**，两套打架。
- **结论**：`application-dev.yml` 里 `spring.ai.vectorstore.pgvector.enabled: false` **显式关掉自动配置**，把控制权交回手写 SQL。**框架给的能力不是越多越好，冲突时要有意识关掉。**

### P15｜🔴 密钥硬编码（最严重的问题）

- **现象**：`application.yml` 里直接写死了两个 key：
  ```
  spring.ai.dashscope.api-key: sk-513d...23fe   # 注释写着"从环境变量读取，避免硬编码"
  spring.ai.deepseek.api-key:  sk-f224...130f
  ```
  注释和实际行为**完全相反**，典型的"复制模板忘了改"。
- **风险**：若该文件曾提交过（仓库里有 `.git`），密钥已泄漏，必须**立即到控制台吊销并轮换**；否则可能被人刷出高额账单。
- **结论**：改成 `${DASHSCOPE_API_KEY}` / `${DEEPSEEK_API_KEY}` 占位，真实值只放根目录 `.env`（已在 `.gitignore`）或环境变量。**面试官看到仓库里有明文 key，是一票否决项。**
